# Release Process (automatic GitHub Release + npm publish)

This repository has two release pipelines, **both driven by tags**; no local publish command is needed:

| Workflow | Trigger | What it does |
|---|---|---|
| [release.yml](../.github/workflows/release.yml) | pushing a `v*.*.*` tag | creates the GitHub Release, with notes generated by GitHub from the commits |
| [publish.yml](../.github/workflows/publish.yml) | pushing a `v*.*.*` tag / a Release being published / manual dispatch | `npm test` → `npm publish --provenance --access public` |

Push one tag and both pipelines run **independently**: the Release is created and npm is published.

> ⚠️ **publish.yml must listen for tag pushes itself; it cannot rely on the release event alone**: release.yml uses
> the repository's built-in `GITHUB_TOKEN`, and GitHub specifies that **events produced by `GITHUB_TOKEN` do not trigger
> other workflows** (to prevent recursion), so the "Release just created" event never reaches publish.yml. That is exactly
> how v0.1.1 was missed — the Release was created, npm had no 0.1.1, and both pipelines looked green. The release-event
> trigger is kept to cover "a human manually publishes a Release in the GitHub UI".

## One-Time Setup: Add NPM_TOKEN

Publishing to npm needs credentials, and credentials are **not stored in code** — only in a GitHub repository secret,
which is never written to logs or exposed in PRs. Nobody (including an AI helping set up the environment) needs to see
the plaintext.

1. Open <https://www.npmjs.com/settings/~/tokens> and click the green **Generate New Token**.
   The new UI goes **straight to the `New Granular Access Token` form**; there is no "Classic Token" entry any more
   (old documentation's "Classic → Automation" cannot be found on today's npm, so do not go looking for it). Fill it in like this:

   | Field | Value | Why |
   |---|---|---|
   | Token name | anything, e.g. `dsh-comfyui-workbench-ci` | Easier to recognise when rotating |
   | Expiration | **90 days** (the longest the UI offers; there is no "never expires") | After expiry, CI publishing fails; see "Rotation" below |
   | **Bypass two-factor authentication (2FA)** | **check it** | Otherwise publishing asks for a phone code and the unattended pipeline hangs |
   | Packages and scopes → Permissions | **Read and write (publish and stage)** | `stage only` **cannot publish** (upload to staging only); this is the easiest field to get wrong |
   | Organizations | **No access** | A personal package does not need org permissions |
   | Allowed IP ranges | **leave empty** | GitHub Actions egress IPs change every time; filling this in guarantees failure |

2. **Copy the token immediately** after saving (it starts with `npm_` and is shown only once; close the page and it is gone forever).
3. Open <https://github.com/TheRealChickenlegs/dsh-comfyui-workbench/settings/secrets/actions> and click **New repository secret**:
   - Name: `NPM_TOKEN` (exactly, character for character — that is the name the workflow reads);
   - Secret: paste the token you just copied, then save.

No code changes are needed after this setup.

> **Rotation**: a Granular token lasts at most 90 days; after expiry `publish.yml` fails at the publish step (401 / permission error).
> Then go back to the token page, delete the old one, generate a new one using the table above, and update `NPM_TOKEN` — **no code or version change needed**.
> Also **never** paste the token into chat, an issue, or a commit: it is equivalent to a password; if you suspect a leak, revoke it on the npm page and regenerate immediately.

> **What if it is not configured?** The guard in `publish.yml` detects the empty `NPM_TOKEN`, **skips** the npm publish and leaves a notice in the run summary —
> the workflow stays green. That way, forks that push tags do not turn red just because a secret is missing.

## Publishing a New Version

```bash
# 1. Change the version (keep three places consistent: package.json / CHANGELOG.md / the tag name)
#    package.json "version"

# 2. Commit
git add -A
git commit -m "chore: release v0.2.0"

# 3. Tag and push (the tag must start with v and match the package.json version)
git tag -a v0.2.0 -m "v0.2.0"
git push origin main
git push origin v0.2.0
```

After pushing the tag:

- the **Release** workflow creates https://github.com/TheRealChickenlegs/dsh-comfyui-workbench/releases ;
- the **Publish to npm** workflow runs next, and on success the new version appears on npm under the name in `package.json`.

`publish.yml` reads the package name from `package.json`, so renaming the package does not require workflow changes.

`publish.yml` first verifies that **the tag name matches `package.json`'s version** —
a mismatch fails immediately with an explanation (`tag is v0.2.0, but package.json version is 0.1.0; refusing to publish.`),
preventing a wrong version from being published (npm **cannot republish** the same version, so this guard is worth a lot).

Another guard is **idempotency**: if the version already exists on npm, `publish.yml` prints a notice and **skips publishing**,
instead of hitting npm's 403. So repeat triggers (for example publishing the Release again in the UI) do not leave failed builds.

## Manual Re-Release / Backfill

- **Backfill the Release for an old tag**: Actions → Release → Run workflow, enter the tag name (e.g. `v0.1.0`). An existing Release is skipped rather than erroring.
- **Manually publish to npm**: Actions → Publish to npm → Run workflow; you can enter a tag (e.g. `v0.1.1`) — it checks out
  **the code that tag points at** and publishes it, guaranteeing "the npm package = the tag's content"; leaving it empty uses
  the default branch's `package.json` version. Versions already published are skipped, so before backfilling an old version,
  confirm it really was never published (otherwise you will see "skipped", not "published successfully").
- **Publish locally by hand** (not through CI, as a fallback):

  ```bash
  npm login --registry=https://registry.npmjs.org
  npm test
  npm publish --access public
  ```

  If the machine is configured with a mirror registry (`npm config get registry`), always specify the official registry explicitly before publishing,
  otherwise it pushes to the mirror (read-only; it fails or reports a permissions error).

## Provenance (verifiable origin signature)

`npm publish --provenance` signs the package with the GitHub Actions OIDC identity: npm shows a **Built and signed on GitHub Actions**
badge, and anyone can verify "this package really came from this build in this repository". That is also what the `id-token: write`
permission in `publish.yml` is for.

Prerequisites: the repository is **public** and `package.json` has a `repository` field — this repository satisfies both.

## What the Published Package Contains

Decided by `package.json`'s `files` field (not `.npmignore`): `lib/` (build output, **committed on purpose**, so users need no
TypeScript), `src/`, `scripts/`, `docs/`, `tsconfig.json`, `cordis.patch.yml`, `icon.svg`, the README, `CHANGELOG.md`, `LICENSE`.

To preview the list before publishing:

```bash
npm pack --dry-run
```
